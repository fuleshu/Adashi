# Shared storage API and SQLite implementation

The interface is implemented in the standalone Rust crate
[adashi-storage-api](../../src-tauri/storage-api/src/lib.rs).
It depends only on Serde, Schemars, serde_json and SHA-256. Its full dependency
tree contains neither SQLite, a server database driver, Tauri nor MCP.
Both application surfaces now compile against its extracted model types.

There are no missing-operation defaults or production panic stubs on the full
traits. ProjectStore implements ProjectStorage and delegates every operation to
StorageClient. SQLite implements all StorageBackend and ReadSnapshot members.
The earlier RuleStorage adapter remains only as a test harness for historical
rules cases. Neither production client can obtain a SQLite connection.

## Operation map

Markdown contract (task 25): `markdown_documents(MarkdownQuery)` returns a bounded
metadata page; `markdown_document(externalId)` returns the complete authored body;
`markdown_backlinks(externalId)` resolves incoming typed references. Query filters
cover explicit IDs, a single association hop, file/symbol bindings and title/body
search. `DesignChange::UpsertMarkdown` and `DeleteMarkdown` use the existing
guarded design transaction. Canonical document identity is `markdown:<externalId>`
and resource identity is `design.markdown`; title changes never rename identity.
The project handle supplies isolation. Validate links against its final staged
graph and reject remaining incoming references on deletion. Prose never cascades
with an architecture owner. Tokens cover only externalId, title, body and ordered
designLinks; generated filenames and headers are not canonical data.

The required methods have no trait defaults. SQLite implements the contract with
schema 15, indexed project-owned documents and ordered associations, token guards
and final-graph validation. Text-format compatibility is handled in the next
adapter phase; it must preserve canonical bodies and sequence identities.

## Local and derived operations

Local registration/settings, rule templates, window state, architecture projection
preferences, file opening, credential lookup and process launch stay outside the
project backend. Existing per-computer mappings are preserved by ComputerCheckout;
moving those mappings into local settings is a later text/server migration decision.

Design-health scans read design_inventory and inspect the current checkout.
Persist their disposable results through LocalDerivedCache::{health,record_health}.
The existing design_element_checks and design_binding_checks are cache data.
The design_health_waivers table is **not** a cache.

SVG rasterization remains in the renderer. LocalDerivedCache::{preview,record_preview}
uses an actual source hash, dimensions and renderer version, avoiding stale images
when independent histories share a numeric revision. Ordinary reads do not write
the cache. Search ordering, prompt composition and AGENTS projection rendering
remain deterministic shared services consuming one snapshot.

QA shell execution is outside backend transactions. StartRun atomically reserves
a run and its job-run records from the selected job versions and frozen command
snapshots. Its QaRun outcome supplies the generated job-run IDs. ClaimJob atomically
claims each reservation before shell execution, preventing duplicate workers.
A worker submits
CompleteJob evidence in short transactions, then CompleteRun computes the group
status/summary from persisted evidence. Retrying any storage operation never
executes a shell command. Preserve the existing per-job history retention inside
CompleteRun, retaining the latest two completed records per job and every active
run. Schema 14 seeds versions for qa.run, qa.job-run, computer, memory.note and
legacy resources during lifecycle migration; these were not previously versioned.

## Transaction obligations

Input preparation validates operation IDs, static required fields, version ranges,
duplicate explicit targets, task state vocabulary, rule lifecycle values, nested
operation IDs and memory budgets. It hashes the complete typed ordered request
using recursively sorted JSON. It does not pretend that static checks can validate
a live model. Each adapter must perform the following under its atomic write unit:

1. Resolve the backend's request receipt before guards. For text storage it is
   scoped to the checkout and stored only in ignored local state. V1 receipts replay only an
   identical fingerprint and return the original typed result. Legacy receipt
   payloads cannot prove request equality and return OperationReused.
2. Check expected versions, including frozen QA job dependencies and both mockup
   versions. Compute design cascade closure and load canonical current documents;
   check_document_tokens returns read_required/out_of_date with complete current
   content and token. Hashes retain the existing adashi.design-document.v1 format.
3. Stage the entire batch. Run the existing shared domain validators: task
   transitions, C4 hierarchy/acyclicity, UML normalization, SVG safety, mockup base
   revisions/status, QA state/evidence, fixed-prompt identity and memory retention.
   Validate every final reference, including retained incoming links on delete.
   check_references checks the final graph supplied by the adapter; it does not
   discover the graph. Design correction results must abort the whole batch.
4. Persist changed aggregates, ordered links, version/tombstone updates and one
   receipt together. Every Change has one ordered ChangeOutcome. For a no-op,
   retain versions/cursor and persist only the runtime receipt. Text no-ops leave
   all tracked files unchanged. Multiple note appends in
   one batch are rejected because retained notes have unique operation provenance.
5. Commit before signaling changes. Failures publish no domain state, receipt or
   cursor. Return CommitUncertain when durability cannot be determined; clients
   retrieve the receipt to resolve it. Map other backend failures to sanitized
   messages. Do not log credentials, driver queries or connection strings.

ReadSnapshot pins one committed instant across all its domain calls. A second
handle can commit while a pinned snapshot continues to show its original state.
Dropping a snapshot releases the read resources; failed transactions roll back.
Closing a handle is idempotent and leaves other handles usable. Polling returns
Unchanged, Changed or Reset; an unknown/foreign/expired cursor requires a fresh
snapshot. Intents expire on the backend's clock and are advisory only.

## Evidence and limits

The standalone crate's tests use a **scripted non-SQLite test double** implementing
every required read and backend method. Domain replies are typed fixtures; its
transaction protocol uses the real preparation, guard, reference and receipt
helpers. It tests all read groups, coherent snapshots, cross-domain publication,
stale guards, failure rollback, no-op replay, content tokens, missing references,
advisory intents and independent handle lifecycle. It is not a production memory
adapter. SQLite has separate real-database tests in storage/sqlite/tests.rs.

The existing application's model reexports preserve serialization and both
transport builds. The historical rules harness now forwards to the complete API.
Task 14 migrated production callers. Task 15's expanded contract, compatibility,
and native desktop/MCP proof is recorded in
[storage-sqlite-validation.md](design-9b39bf9dc98275b9c7d4ebbac8ebb9c213ce496e8205d89779fb933d17d5a050.md).

Intentional implementation changes:
- Schema 14 adds resource-version rows without replacing existing project tables.
- Explicit SQLite initialization selects WAL to permit pinned readers and concurrent
  writers. Copy a SQLite project only after its handles close/checkpoint, including
  its WAL when live; the subsequent text backend is the Git merge solution.
- DesignWrite::EditElement/EditRelationship retain desktop's narrow numeric-version
  guards and load preserved hierarchy/endpoints inside commit. MCP keeps readTokens.
- QaWrite::ClaimJob prevents concurrent retries from executing a reservation twice.
  An interrupted claimed run remains running with evidence retained; retry observes
  its state and never blindly restarts the command.
- New writes use V1 fingerprinted receipts. Old receipts remain readable as Legacy;
  reuse is rejected because historical payloads cannot establish request equality.
- Regenerable health results use the installation-local cache; previews render
  without writing project data. Existing SQL cache tables are retained for upgrade
  compatibility but unused by production reads. Health waivers remain canonical.
