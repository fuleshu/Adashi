# Collaborating through Git text storage

Use **Settings → Project storage → Git text files** to convert an existing
project. Commit `.adashi/storage.json`, `.adashi/text/**` and the generated ignore
rules together. Every collaborator selects their own checkout folder in Adashi;
the project identity and record IDs stay shared. A fresh clone reconstructs its
query data directly from the tracked records.

## Everyday workflow

1. Save or finish the current Adashi edit. Inspect `git status` and `git diff`.
   Commit the complete project change, including its related records; staging
   individual fragments of a transaction can break references.
2. Keep Adashi writes and QA execution idle while running `git pull`, `git merge`
   or `git switch`. The app and MCP may remain open. Git does not participate in
   Adashi's local writer lock, so concurrent Git changes and application writes
   are unsupported.
3. Pull and merge using the team's normal Git workflow. Adashi detects changed
   file content, refreshes the selected project and retains dirty editor drafts.
   A stale save fails. Review the new value, use **Use current value**, and apply
   the intended edit again. MCP callers reread the resource/document and use the
   returned version/readToken; never replace a stale token without reviewing data.
4. After a merge, read the project in Adashi or MCP before publishing the result.
   A clean Git merge can still have invalid references, duplicate numbers or
   ambiguous ordering. Resolve any errors explicitly, inspect the final diff,
   commit the resolution, and push.

Adashi performs no Git commands and never chooses a conflict winner. Independent
task/QA additions use separate UUID records. References keep the UUID identity.
All numeric IDs retain SQL AUTOINCREMENT behavior; task and QA display numbers
use the project maximum plus one. Use API IDs to address tasks/jobs. Offline clones
can choose the same next ID/number: validation rejects the collision, never silently renumbering.
An explicitly reviewed correction preserves UUID identities and references and
updates the affected numeric resource keys and textual dependencies together.

## Resolving conflicts

* **Overlapping text or delete/edit:** inspect both Git versions and resolve the
  affected records. If retaining a deleted object, also restore the related
  ordered links and inspect deletion/version provenance. Retain the other user's
  independent changes. Do not apply a blanket "ours" or "theirs" to the project.
* **Delete/reference:** Git may report success while a newly added link refers
  to a tombstone. Adashi blocks dependent reads and writes. Explicitly restore
  the target with its necessary related records, or remove the unwanted link.
* **Reordered task/QA links:** each entry needs a distinct nonnegative
  `sort_order` within its owning task/job and collection. Gaps are allowed.
  Two independently moved entries at the same position are a validation error,
  even if Git merged their files cleanly. Decide the combined order explicitly.
  Mockup annotations retain their existing `(sort_order, id)` tie-break semantics.
* **Multiline content:** preserve the `lines` chunks and their terminators.
  Validate the resulting Mermaid/SVG/document as well as JSON syntax.
* **Unresolved markers or invalid JSON:** reads and writes fail without repairing
  or rewriting tracked files. Resolve the files externally, then retry/reload.

Edits to separate resources merge cleanly. Separate fields of the same resource
can also merge, but nearby fields and shared `updated_at` changes can cause normal
Git conflicts. The format makes no promise of conflict-free same-resource edits.
Even when both branches have equal stored counters, their content fingerprints
invalidate stale guards after a merge or branch switch.

## Interrupted writes and local data

A process interruption releases its OS lock. The next client completes a prepared
transaction from `.adashi/local/text-transaction.json` before exposing data, then
resolves the original request from local retry state. Retry with the **same operation
ID and request in the same checkout** when the previous outcome is uncertain.

An unexpected external edit to a journaled file blocks recovery and preserves both
the edit and journal. Stop writers, back up those files, compare the affected file
with the journal's before/after images, and explicitly reconcile it before retrying.
Do not delete a prepared journal or guess that a partial set of files is complete.
These checks cover process interruption, not a universal power-loss guarantee.

Reads, polling, fresh requests with no persistent SQL effect and identical retries
preserve all tracked bytes and mtimes. A fresh content-equivalent SQL upsert can
consume an ID; its sequence tombstone is persisted to preserve the original SQL
allocation behavior. Identical retries do not consume another ID.
Request retry results live only in ignored `.adashi/local/`,
shared by desktop and MCP in that checkout. A clone receives project content and
starts with no request history. Cross-clone request replay is not guaranteed.

For an older version-1 text project, the next successful content write performs a
one-time format upgrade: it removes tracked `mutation_operations` files and writes
format version 2. Review and commit those deletions and the format marker together.
Opening a project only for reading preserves its files. Existing Git commits are
not rewritten; the retired files disappear from subsequent project snapshots.

Ignore `.adashi/local/**`, database backups/sidecars, locks, journals, caches and
temporary publication files. Computer checkout mappings and credentials stay in
local settings/state. User-authored commands and documents can contain paths or
secrets themselves; review them before committing. Absolute QA working directories
are preserved with a migration warning. Git is not a distributed execution lock:
do not copy a running QA reservation as authorization to execute it elsewhere.

Text/SQLite conversion preserves IDs, references and retained evidence, but it
changes the selected backend for the project. Coordinate that change before
committing the portable descriptor. Conversion back to an already populated
destination requires the explicit backup-and-replace choice.

## Repeatable verification

Build the frontend and both native binaries, then run:

```powershell
cargo test --manifest-path src-tauri/Cargo.toml --offline
python -B scripts/check_git_collaboration.py --binary src-tauri/target/debug/adashi-mcp.exe
$env:ADASHI_PLAYWRIGHT_PACKAGE = '<path to the Playwright package>'
node scripts/check_native_git.mjs '<printed target/git-collaboration directory>'
```

The Python suite creates a local bare remote and independent clones under
`target/git-collaboration/<run-id>`. It uses real commits/pushes/pulls/merges and
independent stdio MCP processes; it never contacts a network remote or changes the
source checkout's Git history. The native suite uses those dedicated clones,
isolated settings and a real Tauri WebView2 process. Git histories, command results,
JSON evidence and native screenshots remain in that directory for inspection.

The suites cover simultaneous task/QA additions, stable IDs/references, clean
reconstruction, separate and overlapping edits, same-resource fields, multiline
artifacts, delete/edit and delete/reference, display-number and ordering collisions,
two local processes, tracked read/no-op stability, local retry replay, real writer
termination during partial publication, recovery with external interference,
native pull/branch reversal/conflict recovery, stale drafts/readTokens and native
text/SQLite/text conversion of the merged clone.
